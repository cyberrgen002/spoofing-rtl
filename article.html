Security research proof-of-concept. Brave bug bounty, finding F28 (Brave iOS Reader Mode). Benign: stores nothing, sends nothing, collects nothing.

Step 1 of 3. The reader-mode glyph should now be visible in the URL bar. Tap it. Then follow the instructions that appear inside the reader view.

F28-POC-TITLE :: THIS TITLE CAME FROM THE ATTACKER ORIGIN

F28-POC-BYLINE :: THIS BYLINE CAME FROM THE ATTACKER ORIGIN

F28-POC-BODY — IF YOU ARE READING THIS TEXT WHILE THE ADDRESS BAR SHOWS A DIFFERENT SITE, BRAVE HAS RENDERED THIS ATTACKER-AUTHORED DOCUMENT AS THAT SITE'S ARTICLE. THAT IS THE BUG.

STEP 2 — you are now in reader mode on the attacker's page. Tap the large link below. It navigates to an ordinary website that has no article on it. Watch the reader-mode glyph in the URL bar as you go: it will stay visible, which is already wrong.

STEP 2 — TAP HERE TO GO TO THE VICTIM SITE

STEP 3 — once the victim page has loaded, tap the reader-mode glyph again. This text will reappear, unchanged, underneath the victim's address. Nothing on that screen will name this origin.

This page exists so that Brave for iOS will run Mozilla Readability over it and keep the parsed result. It is deliberately shaped like an article: it lives at a non-root path, it is served over https, and it carries enough prose that Readability's isProbablyReaderable heuristic scores it well above the threshold it needs before the reader-mode affordance is offered at all. None of that is unusual; every ordinary news article satisfies the same conditions, which is why the condition is not a meaningful barrier.

Brave iOS keeps the parsed article for a tab in a single field on the tab helper. The parsed result is stored on its own, without the URL of the document it was parsed from recorded anywhere alongside it. When the reader-mode button is later tapped, the helper takes whatever happens to be in that field and writes it into the reader cache under the URL that is committed in the tab at that moment, then loads an internal reader page whose query parameter carries that same URL. The address bar for an internal reader page prints the URL taken out of that query parameter, so the omnibox shows the committed site while the body shows the stored article.

Two of those steps are individually reasonable and only the combination is wrong. Caching the parsed article is a sensible optimisation, because parsing is expensive and the user may toggle reader mode on and off repeatedly. Keying the reader cache by URL is also sensible, because the cache has to be looked up again when the internal page loads. What is missing is the binding between the two: nothing ever compares the URL the article was parsed from against the URL it is being filed under, even though the parsed result carries its own URL field that would make the comparison a one-line change.

There is a guard, and on an ordinary navigation it works. When a navigation starts, the helper clears the stored article, precisely so that the article from the previous page cannot survive into the next one. That guard, however, has an exception written into it: if the page being navigated away from is itself a reader-mode page, the clear is skipped entirely. The stated reason is that a reader-mode page can trigger sub-navigations of its own after activation, and clearing on those would break it. The exception does not distinguish a sub-navigation from a plain link to another site, so any link followed out of the reader view carries the stored article with it.

The same exception is written a second time, in the code that decides whether to hide the reader-mode glyph while a navigation is in flight. That code also skips its work when the page being left is a reader-mode page. The two exceptions compose: the article survives, and the glyph is never even taken off the screen, so there is no moment at which the interface admits that anything changed.

The final step needs no trickery at all. When the destination page reports back that it is not suitable for reader mode, the helper ignores the reported state and merely notifies its observer that something changed. The observer recomputes whether the glyph should be visible, and it computes that purely from whether the stored article field is non-empty. Because the field was never cleared, the answer is yes, and the glyph stays on a page that has just finished saying it has no article to show.

The consequence is content spoofing rather than script execution. The internal reader page is served with a restrictive content security policy that permits scripts only with a per-load nonce, so markup carried in from this document does not run. What the attacker gets instead is the ability to place arbitrary prose, headings and a byline underneath another site's name, its real address-bar text, and its ordinary transport-security treatment, with nothing on the resulting page naming where the content actually came from. The reader template has no field for the source domain, so the page cannot contradict the address bar even in principle. Because the reader cache is backed by disk, the substitution also survives until the entry is replaced.

The fix is small and Brave has already written it for the other platform. On desktop, the equivalent component was given the URL of the request it was created for and now re-checks that URL against the response before it is allowed to supply a body, with a comment stating that distilled content belongs to the page it was distilled from and must never be sent as the body of any other URL. That is exactly the invariant this page demonstrates is absent on iOS. Recording the URL next to the stored article and refusing to file it under a different one would close the whole chain, regardless of how the field came to survive.
